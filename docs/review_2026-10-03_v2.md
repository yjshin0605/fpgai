# 수정 2차 RTL 전체 검토 — 2026-10-03

검토한 RTL 커밋: `b1a499af0a547ed60e4b15547fb479e0463efdfe`.
사용자가 수정한 `spec_feat(2).v`, `spec_feat_axi(2).v`를 각각 정식 파일명으로 반영했다. RTL 자체에 추가 수정은 하지 않았다. 나머지 5개 모듈도 함께 검토했으며 시뮬레이션 소스 7개의 Git blob 해시가 이 커밋과 모두 일치한다.

**결론: 기본 산술은 이번 검사에서 일치하지만, 연속 레코드 연결·중간 리셋·AXI 응답 순서는 수정이 필요하다.** 아래에서 확정 재현과 입력/운영 조건에 따른 위험을 구분한다.

## 1. 우선 수정할 문제

### P1 — 결과를 버린 뒤 서로 다른 레코드를 결합함 (재현)

위치: `spec_feat.v`의 `pair_ready`, `tr_done/eh_done`, 갈래별 보관 로직.

갈래별 보관 공간이 한 개이고 입력 `ready`는 항상 1이다. 먼저 온 결과 A를 보관 중 다음 결과 B가 오면 B를 버리고 `pair_err`를 낸다. 이후에도 레코드 번호 없이 다음 도착값과 결합하므로 짝이 밀린다. STATUS의 오류 비트만 지워서는 복구되지 않는다.

재현 입력: FFT 3레코드(각 127×256클럭), DC 3레코드(각 16,384클럭)를 동시에 시작해 각 갈래에서 쉬지 않고 전송. DC는 레코드별 I=1024/2048/3072, Q=0, norm_sh=0.

| 항목 | 정상 기대 | 관측 |
|---|---|---|
| 결합 결과 개수 | 3 | 2 |
| 결과 1 mean_q8 | 256 | 256 |
| 결과 2 mean_q8 | 512 | **768** |
| 결과 3 | 존재 | 없음 |
| pair_err | 0 | 1회 발생 |

FFT B에 DC C의 특징이 붙었다. PS shadow는 첫 결과를 정상 보관하므로 이 문제는 shadow 덮어쓰기와 별개다. 실제 앞단이 이 전송 패턴을 만들지는 앞단 연결에 달렸지만, 현재 인터페이스는 이 합법적 입력 패턴을 막지 않는다.

개선: 두 갈래에 레코드 ID와 FIFO를 두고 동일 ID끼리만 결합하며 overflow 시 명확한 중단/폐기/재동기화 절차를 둔다. 장기 평균 속도가 다르면 FIFO만 늘려도 결국 넘친다. 레코드 시작 제한 또는 입력 backpressure가 함께 필요하다. 임시로 한 레코드를 넣고 결과를 읽고 done을 지운 뒤 다음 레코드를 시작하면 이 재현 조건을 피할 수 있다.

### P1 — 계산 중 리셋 후 hist가 남음 (재현)

위치: `traj_rec.v`의 `hist`, `initial`, `S_PASS`, `S_SCANH`.

`hist`는 initial로만 초기화되고 rstn에서 지워지지 않는다. 정상 완료 때 SCANH가 지우지만 PASS/SCANH 도중 리셋하면 일부가 남는다. initial은 매 rstn마다 다시 실행되지 않는다.

작은 N_FR=4 진단: hist[42]=2에서 리셋 후 모두 무효인 4프레임을 입력하자 **n_active=0, hmax=2**. 기본 127프레임 사용자 smoke에서도 리셋 후 첫 결과가 **n_active=0, hmax=7**이었다. 두 번째 레코드만 깨끗했다.

현재 AXI 헤더의 ‘첫 레코드 버리기’는 주석/소프트웨어 계약이며 RTL은 첫 결과에도 done/irq를 올린다. PS 예시에는 첫 결과 폐기가 없다.

개선: 초기화 FSM으로 256칸을 지우고 완료 전 입력을 차단하거나, 초기화 중 데이터를 안전하게 보관한다. 단순히 256클럭 기다리는 것만으로 현재 코드는 지워지지 않는다. 임시 우회는 양쪽 갈래가 정상 정렬된 완전한 더미 레코드를 처리하고 그 결과를 버리는 것으로, 입력 중간 리셋으로 생긴 프레임 정렬 문제까지 해결하는 것은 아니다.

### P1 — AXI BVALID/RVALID가 핸드셰이크 완료 전에 올라감 (재현 + 규격 확인)

위치: `spec_feat_axi.v` 177–180, 213–217행.

AWREADY/WREADY와 BVALID, ARREADY와 RVALID를 각각 같은 분기에서 동시에 NBA로 올린다. 그 에지 직전 READY는 0이므로 요청은 아직 수락되지 않았다. 응답 VALID가 먼저 올라오고, 다음 에지에 요청과 응답이 함께 전송될 수 있다.

진단에서 쓰기/읽기 모두 ‘이전 완료 요청 0개인데 응답 VALID=1’이 관측됐다. 간단한 레지스터 읽기/쓰기가 성공하는 것과 규격 준수는 별개다.

개선: 실제 AW/W 수락을 저장한 뒤 BVALID를 올리고, AR 수락 후 RDATA/RVALID를 생성한다. WSTRB=0도 데이터 변경 없이 정상 응답은 해야 한다. 주소와 데이터를 둘 다 기다리는 정책 자체를 오류로 판단한 것은 아니다.

근거: [AMD PG101 AXI Protocol Checks](https://docs.amd.com/r/en-US/pg101-axi-protocol-checker/AXI-Protocol-Checks-and-Descriptions), `AXI_ERRS_BRESP_AW / WLAST`, `AXI_ERRS_RID`. 이번 시험은 자체 간단한 순서 검사이며 Vivado AXI VIP 전체 검증은 아니다.

## 2. 값·동작 조건에서 주의할 부분

### CORDIC 출력 포화로 피크 위치와 대역폭이 달라질 수 있음

25비트 입력 전체 범위를 18비트 출력과 OUT_SHIFT=4로 보존할 수 없다. 내부 28비트는 충분하지만 출력은 262,143에서 포화된다. 입력 벡터 크기가 대략 255만을 넘으면 포화가 시작된다(정확 경계는 정수 반복 오차에 좌우됨).

예: Re=3,000,000 및 6,000,000, Im=0은 모두 출력 262,143이 된다. 같은 프레임에서 서로 다른 크기의 두 피크가 같은 값이 되어 작은 fftshift 빈 번호가 선택될 수 있다. 포화된 피크의 1/4로 대역폭 문턱을 만들기 때문에 대역폭도 넓게 셀 수 있다.

주석의 실측 최대 1,138,443이 실제 전 입력의 보장 범위라면 현재 설정이 충분할 수 있다. 실측 최대와 인터페이스 최대는 구분해야 한다. FFT 스케일링으로 최대를 보장하거나 OUT_SHIFT/OUT_W를 바꾸고 특징 문턱 및 골든도 함께 맞출 것.

### norm_sh와 skip_frames가 레코드별로 저장되지 않음

norm_sh는 입력 당시가 아니라 env_detect 4단에서 읽는다. 마지막 입력 직후 배율을 바꾸면 파이프라인에 남은 이전 샘플에도 새 값이 적용된다. skip_frames도 traj_rec에 각 프레임이 도착할 때 적용된다. 두 값 모두 레코드 시작 전에 설정하고 해당 처리가 끝날 때까지 유지해야 한다. 연속 레코드마다 값을 바꾸려면 설정값을 레코드/샘플과 함께 전달해야 한다.

PS 배율 계산의 최대값은 **DC 제거 후 실제 I/Q** 기준이어야 한다. 원본 DMA 샘플 최대를 그대로 대신 쓰면 전처리 결과와 다를 수 있다. 완전 0인 레코드는 log2/bit_length 기반 식의 별도 처리가 필요하다. 이 저장소 RTL만으로 PS 계산 구현은 검증할 수 없다.

### busy·COUNT·오류 비트의 의미

busy는 `traj_rec` 계산 FSM만 나타낸다. 프레임/샘플 수집 중이나 짝 대기 중에도 0일 수 있으므로 전체 완료나 설정 변경 허가 신호가 아니다.

COUNT는 `spec_feat.regs_valid` 개수다. shadow가 가득 차 버린 결과도 세고, 짝 결합 전에 버려진 갈래 결과는 세지 않는다. 현재 shadow의 레코드 ID 또는 원래 입력 레코드 수로 사용하면 안 된다. 32비트이므로 2^32번에 wrap한다.

PS는 특징을 다 읽기 전에 done을 지우면 안 된다. STATUS bit2=ovr, bit3=pair_err를 확인해야 한다. pair_err를 W1C로 지워도 데이터 순서는 복구되지 않는다. 제공된 PS 예시는 done만 확인해 오류를 놓친다.

### 클럭·리셋·입력 경계

`clk`와 `s_axi_aclk` 사이 CDC가 없으므로 동일한 클럭 연결이 필수다. ‘같은 주파수’의 독립 클럭은 충분하지 않다. AXI reset은 인터페이스, rstn은 데이터와 설정을 각각 초기화하므로 리셋 절차도 함께 정의해야 한다.

DC는 16,384 valid 개수, 궤적은 127 fr_valid 개수로 레코드를 나눈다. DC 측 TLAST/record ID가 없고 traj_rec는 fr_frame을 skip 비교에만 사용한다. 샘플 하나/프레임 하나가 누락되거나 중간부터 재시작하면 경계가 계속 밀릴 수 있다. traj_frame도 256개 빈의 중복/누락, TLAST 위치를 검사하지 않는다. 정상적인 valid 공백 자체는 문제없다.

traj_frame의 약 130클럭 스캔은 정상 256빈 프레임 간격에서 충분하고, traj_rec 계산은 정상 32,512클럭 레코드 간격보다 짧다. malformed TLAST나 traj_rec 단독 사용으로 입력을 더 빨리 보내면 계산 중 start가 유실될 수 있다.

### 근사식·특징 정의와 주석 불일치

- env=max+3/8 min의 연속식 최대 과대오차는 약 **6.8%**로, ‘최대 약 4%, 히스토그램 칸을 바꾸지 않음’은 맞지 않는다. I=950,Q=350은 현재 정수식 env=1080 → bin1, 실제 제곱근 약1012.42 → bin0이다. 학습/골든도 같은 근사식을 쓰면 근사 자체가 곧 RTL 버그인 것은 아니다.
- 작은 값에서 분수항을 각각 먼저 버리고 배율을 나중에 적용한다. 입력을 먼저 정규화한 골든과는 같지 않을 수 있다. 예: I=Q=3, norm_sh=8이면 현재는 768, 먼저 I/Q를 256배 한 뒤 근사하면 1056이다.
- `mono`는 ±방향 차이 자체가 아니라 **절댓값**이며, 크기 1..4 이동만 센다. 양/음 이동 방향을 PS에서 복원할 수 없다.
- `rep_lag`는 모든 반복 점수가 0이면 **0**이다. 주석의 ‘동점이면 작은 L’을 모든 경우에 적용한다면 2와 다르다. ‘매칭 없음’ 센티널로 0을 쓰는지 골든/분류기 계약을 확정할 것.
- peak=0..3이면 peak>>2=0이어서 0인 빈까지 세어 `fr_c=256`이 된다. invalid=1이면 궤적 합계에서 제외되지만 invalid=0이면 넓은 대역폭으로 집계한다. 피크 0일 때의 정책을 정해야 한다.
- cordic_mag 헤더의 ‘>>>1, 16비트’는 실제 >>>4, 18비트와 다르다. env 경로 주석 일부의 ‘정규화된 I/Q’, AXI WSTRB ‘쓰이지 않음’도 현 코드와 다르다.

## 4. 이번 수정에서 개선된 부분과 검증

- WSTRB=0000 및 byte1만 켠 쓰기가 norm_sh/skip_frames를 변경하지 않음: 재현 시험 통과.
- done=1일 때 shadow를 보존하고 새 결과를 버리며 ovr를 세움: 첫 값111, 다음 값222를 주입해 shadow111/ovr1/count2 확인.
- 별도 출력 스냅샷과 consume/arrival 처리로 보관값이 사용된 순간 새 도착값을 남기는 코드 구조는 개선됨. 단, FIFO overflow 후 짝 복구 문제는 남아 있음.
- 단일 전체 레코드: n_active127, pairs126, zero126, rep_max125, lag2, bw_sum127, mean_q8=256. 중간 valid 공백과 태그 지연 포함 통과.
- 독립 Python 정수 참조와 **1,413개 값 비교 통과**: env_detect800벡터(32개 shift 전부), CORDIC206벡터, traj_frame25프레임의3값, traj_rec24레코드의13값, env_hist5레코드의4값.
- 사용자의 smoke는 PASS지만, 연속 항목이 결과를 읽고 다음 레코드를 보내므로 진짜 겹친 연속 입력을 검증하지 않는다. 리셋 항목도 첫 결과를 버린 후 두 번째만 검사한다. PASS를 위 문제 해결 증거로 보면 안 된다.

검증은 Icarus Verilog12.0 RTL 시뮬레이션이다. 모든 가능한 입력의 증명, 새 학습/골든 데이터 전체 비교, Vivado 합성·타이밍·자원·CDC 및 보드 검증은 수행하지 않았다. 앞단 FFT IP/전처리 및 PS 드라이버는 이번 7모듈 검토 범위 밖이다.

## 5. 재현 방법

저장소 루트에서 Icarus Verilog와 Python3를 준비한 뒤:

```sh
python3 tests/review_v2/check_numeric.py --rtl .
sh tests/review_v2/run.sh
```

`check_numeric.py`는 불일치 시 실패한다. `run.sh`의 세 진단 벤치는 알려진 문제의 관측값을 출력하며, 출력에 나온 오류 재현을 정상 제품의 PASS로 해석하면 안 된다. 로그는 `tests/review_v2/results.txt`에 보관했다. 이전 `tests/review/`는 구버전 검토 당시 자료로 그대로 유지했다.
